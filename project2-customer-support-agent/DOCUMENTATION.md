# Project 2 Documentation: E-commerce Customer Support Agent

A plain-language guide to what this project is, what it is built from, what data it uses, and how every file fits together.

---

## 1. What is this project?

This is an AI customer-support agent for an online store. A customer chats with it, and in one conversation it can:

| Customer says | What the agent does | How |
|---|---|---|
| "Where is order ORD-001?" | Looks up the order and reports shipping status | Calls an order-lookup service |
| "Please refund my Kindle (ORD-002)." | Starts a refund and returns a refund ID | Calls a refund service |
| "What are the Platinum tier benefits?" | Answers from the store's product and policy catalog | Searches a knowledge base (RAG) |
| "Hi, I'm Jane, I like short answers." (later, in a new chat) "Do you remember me?" | Remembers the name and preference | Long-term memory |
| "I'm Gold with 4250 points, what's my discount on $150?" | Gives an exact breakdown | Runs real code in a sandbox |
| "Go to udacity.com and tell me the page title." | Reads a live web page | Browser tool |

The agent runs **in the cloud** on Amazon Bedrock AgentCore, so anyone with permission can call it, not just a script on one laptop.

## 2. The technologies, and what each one does

| Technology | Plain-English role | Where it is used |
|---|---|---|
| **Amazon Bedrock AgentCore Runtime** | Hosts the agent in the cloud and gives it a callable endpoint. | Deployed with `agentcore deploy` |
| **Strands Agents SDK** | The Python library that builds the agent: model, tools, hooks. | `main.py` |
| **Amazon Nova 2 Lite** (`global.amazon.nova-2-lite-v1:0`) | The language model that understands the customer and decides which tool to use. | `main.py` |
| **AgentCore Gateway + MCP** | A "tool door". It exposes backend services to the agent using the Model Context Protocol, a standard way to describe tools. | Created in AWS; used via `MCPClient` in `main.py` |
| **Amazon API Gateway (REST)** | Turns the order Lambda into three web routes. | Routes `/orders/{id}`, `/customers/{id}`, `/customers/{id}/orders` |
| **AWS Lambda** | Small backend functions: one for orders, one for refunds. | `lambda/order_tracker.py`, `lambda/refund_processor.py` |
| **Bedrock Managed Knowledge Base** | Stores and searches the product catalog so answers are grounded in real text (**RAG**, Retrieval-Augmented Generation). | `search_knowledge_base` in `main.py` |
| **Amazon S3** | Holds `product_catalog.txt`, which the Knowledge Base reads. | Created during setup |
| **AgentCore Memory** | Remembers customers across separate conversations, using two strategies: *facts* (e.g. "name is Jane") and *preferences* (e.g. "likes concise answers"). | `MemoryHook` in `main.py` |
| **AgentCore Code Interpreter** | A secure sandbox that runs Python, so maths is exact instead of guessed by the model. | `calculate_loyalty_discount` in `main.py` |
| **AgentCore Browser tool** | Lets the agent open and read live web pages. | `AgentCoreBrowser` in `main.py` |
| **uv / pyproject.toml** | Installs the Python dependencies. | `pyproject.toml` |
| **IAM roles** | Permissions for the Lambdas, the Gateway and the deployed agent. | `setup_permissions.py` plus roles made during setup |

## 6. Inside `main.py`

The file is built in this order:

1. **App.** `app = BedrockAgentCoreApp()` creates the web server AgentCore talks to. At the bottom, `app.run()` starts it.
2. **Configuration.** Four values: `GATEWAY_URL`, `KB_ID`, `REGION`, `MEMORY_ID`.
3. **Clients.** The Nova model, a memory client, and a Bedrock Knowledge Base runtime client.
4. **`get_namespaces()`.** Asks the Memory resource how its strategies are stored (for example `cs_agent/{actorId}/facts`). It accepts the newer `namespaceTemplates` field and the older `namespaces` field.
5. **`MemoryHook`.** Plugs into the agent's lifecycle:
   - *Before each reply*, it searches memory for things relevant to the customer's message. Results are tagged by type and added in front of the message as `Customer Context:`.
   - *After each reply*, it saves the customer's question and the agent's answer as a memory event, for later.
   - If memory fails, the error is logged and the customer still gets an answer.
6. **`search_knowledge_base`.** A tool that asks the Knowledge Base for matching passages and joins them with `---`. If no Knowledge Base is configured it says so instead of crashing.
7. **`calculate_loyalty_discount`.** A tool that writes a small Python program with the customer's numbers filled in, runs it in the Code Interpreter, and returns the JSON result. The rules: redeem points in blocks of 500, never more than 50% of the order, then apply the tier discount to what is left. If the sandbox is unavailable, it falls back to a tier-only discount.
8. **`invoke()`.** The entry point for every request:
   1. Read `prompt`, `customer_id` and `session_id` from the request (create a session ID if missing).
   2. Create the memory hook and the browser tool.
   3. Open the MCP connection to the Gateway and load its six tools.
   4. Build the agent with all tools, the hook and the system prompt, and ask it the question.
   5. Return the text of the reply. Any error becomes a friendly message.

   The agent is built and run **inside** the open Gateway connection. If the connection closed first, the Gateway tools would stop working.

### Worked example: the loyalty question

> "I am a Gold member with 4250 points. Calculate my discount on a $150 standard order."

- 4250 points rounds down to 4000 (blocks of 500). The cap is 50% of $150 = $75 = 7500 points, so 4000 is allowed.
- 4000 points = **$40.00** off, leaving $110.
- Gold gets 10% off $110 = **$11.00**.
- **Final total $99.00**, total savings $51.00.
- Points earned on $99 (standard, 1 per $1) = 99. Remaining points = 4250 - 4000 + 99 = **349**.

## 7. How it was set up and deployed (order of operations)

**Backend (cloud resources, all in `us-east-1`):**

1. Create the two Lambdas from `lambda/` (Python 3.12) with a basic execution role.
2. Create the REST API with three GET routes linked to the order Lambda, give each method a `200` response, and deploy to a `prod` stage.
3. Create the AgentCore Gateway (no authorizer, lab only) with two targets: `order-tracker` (the API) and `refund-processor` (the Lambda plus `lambda_schema`).
4. Upload `product_catalog.txt` to S3, create a Managed Knowledge Base on it, and sync.
5. Create the Memory resource with the two strategies.
6. Put the four IDs into `main.py`.

**Deploy:**

```
uv sync --python 3.13
uv run agentcore configure --entrypoint main.py --name csagent --deployment-type direct_code_deploy --runtime PYTHON_3_13 --disable-memory
uv run agentcore deploy            # packages main.py and creates the cloud runtime
uv run setup_permissions.py        # grants the agent access to KB, Memory, Browser
agentcore invoke '{"prompt": "...", "customer_id": "CUST-123", "session_id": "t1"}'
```

## 8. What happens on one request

1. `agentcore invoke` sends the JSON to the runtime, which calls `invoke()`.
2. The customer's message is added to the conversation. The memory hook fires, finds earlier facts, and prepends them.
3. The model reads the message and decides which tool to call (or none).
4. The tool runs: Gateway to Lambda, Knowledge Base search, sandbox, or browser.
5. The tool result returns to the model, which writes the final answer.
6. The memory hook saves the question and answer.
7. The answer goes back to the customer.

## 10. Problems met and fixed

| Problem | Cause | Fix |
|---|---|---|
| `main.py` could not import the browser tool | `strands-agents-tools` 0.9.0 removed it | Pinned `<0.9` in `pyproject.toml` |
| Gateway rejected the order API target | The Gateway reads the API's OpenAPI export, and methods had no response defined | Added `200` responses and redeployed `prod` |
| Gateway target creation failed on a name | Target names may not contain underscores | Named them `order-tracker` and `refund-processor` |
| Knowledge Base returned nothing at first | The sync job was still running | Waited for sync to finish |
| AWS rejected valid-looking keys | Key, secret and token were from different lab sessions | Regenerated all three together |

## 11. Before using this in production

- **Security.** The Gateway has no authorizer here, which is fine only for a lab. Use OAuth or signed requests.
- **Cost.** The Knowledge Base's vector store is the main always-on cost. Delete it when idle and set budget alarms.
- **Monitoring.** Turn on tracing for the Gateway and Memory so CloudWatch shows full request traces.
- **Real data.** Replace the mock orders and refunds with real systems, and validate tool inputs and outputs.
